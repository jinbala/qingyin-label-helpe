## 1. 背景与目标

### 1.1 背景

v1.4.8 已完成一轮性能、存储与工程化维护：保存路径减少序列化、设计器编辑分级校验、条码单次编码、PDF 让出时间片、纯 Node 构建、根 `package.json` / CI / Prettier / EditorConfig、存储配额前置拦截等。现有自动化测试 58 项，行覆盖率 88.55%。

复审又确认了两个应当优先处理的缺陷：

1. 存储中存在单个无法解析的模板或位置时，页面回退到默认模板，随后任意一次保存都会把其余自定义模板当作「已删除」提交，存在**整库丢失**风险。
2. CODE128 编码非法内容（中文、空文本）时，JsBarcode 抛出的是字符串而不是 `Error`，界面把它显示成 `undefined`。

同时确认了若干可量化收益的优化项：内容缩放导致文字裁切、保存路径引用短路未生效、PDF 体积在生成后才检查、备份数量上限与 UI 不一致、图片导入总是重编码 PNG 等。

### 1.2 目标

在不扩大权限面、不引入构建工具、不改变打印输出与现有通信协议的前提下：

1. 消除已知的数据丢失路径，保证任何加载失败都不会触发隐式删除。
2. 所有用户可见错误都有可读中文说明，不出现 `undefined`、原始英文或堆栈。
3. 完成剩余的保存、渲染、PDF 生成与页面启动性能优化。
4. 补齐容量边界（PDF 体积、备份数量、图片格式、存储估算）的预检与提示。
5. 补齐回归测试与真实浏览器冒烟验证，覆盖率目标 ≥ 90%。

### 1.3 成功指标

| 指标 | 现状 | 目标 |
| --- | --- | --- |
| 加载异常导致模板被删 | 可复现 | 0 例；有回归测试 |
| 用户可见 `undefined` 错误 | 可复现（CODE128） | 0 例 |
| 保存 8 MB 库（内容未变） | 约 43 ms，未改动模板仍被 JSON 比较 | 未改动模板不再序列化；实测 ≤ 20 ms |
| 超 12 MB PDF | 生成完成后才拒绝 | 生成前/生成中提前拒绝，不出现长时间等待后失败 |
| 行覆盖率 | 88.55% | ≥ 90%（浏览器专属文件单列说明） |
| 自动化测试 | 58 项 | ≥ 65 项，全部通过 |
| 新权限 / 新运行时依赖 | 无 | 保持无 |

### 1.4 设计原则

- **数据安全优先**：任何异常路径都不得自动删除已有模板或位置。
- **最小权限**：不申请 `unlimitedStorage`，不扩大 `host_permissions`，不引入远程资源。
- **零构建**：源码目录仍可直接加载为扩展；不引入打包器、框架或 TypeScript。
- **输出稳定**：除明确列出的行为变更外，打印 PDF 的页面尺寸、像素结果与现有版本一致。
- **错误可读**：面向用户的中文文案，不暴露英文库错误、`undefined` 或堆栈。
- **可回滚**：存储 schema 不升级；新增行为尽量通过默认值或特性开关过渡。

## 3. 详细需求

### 3.1 REQ-DATA-01（P0）加载容错与禁止隐式删除

**问题**

`src/ui/app.mjs` 的挂载逻辑把「读取设置」和「解析设置」放在同一个 `try` 中。`createSettingsClient().loadSettings()` 会先把完整设置保存为 `baseline`；随后只要有一个模板或一个 layout 校验失败，整个解析抛错，页面回退到 `defaultTemplates()`。下一次保存时，`settingsPatch(baseline, next)` 会把 baseline 中存在、回退状态中不存在的所有模板写入 `deletedTemplates`，后台 `applySettingsPatch()` 随即删除它们。

**需求**

1. 设置加载必须逐项校验：
   - 每个模板单独 `localTemplate()`，失败项跳过并记录原因（模板 id / 名称 / 错误）。
   - 每个 layout 单独 `normalizeLayout(layout, template.width, template.height)`，失败项跳过并记录。
   - 有效项照常进入 `state.local` / `state.layouts`，`selected` 在有效项中回退。
2. 页面顶部显示一条警告，列出被跳过的项数与前 3 个名称；不确定时提示「请先导出/检查存储，再删除重试」。
3. 「删除」只能由用户显式操作产生：
   - `commit()` 接受显式的 `deletedTemplates` / `deletedLayouts`（或等价机制）。
   - `settingsPatch()` 不再仅凭「当前状态缺失」推断删除；至少要在 `loadIncomplete` 为 true 时禁止发送删除列表。
4. 如果 `loadSettings()` 本身失败（后台读取失败），沿用现有行为：保存被阻止，并提示刷新。
5. 挂载时不得自动写回存储。

**验收标准**

- 构造存储：2 个有效自定义模板 + 1 个 `productName` 超长模板；刷新后显示 2 个有效模板和 1 条警告。
- 随后点击模板卡片、保存位置、编辑并保存模板：重新读取存储，2 个有效模板仍存在，坏模板未被隐式删除。
- 构造存储：模板全部有效，但其中 1 个 layout 含未知 part；刷新后模板正常显示，坏 layout 被忽略并有警告；保存其他位置不会删除任何模板。
- 后台读取失败时，保存按钮/保存动作给出「本地模板尚未读取成功」并拒绝写入。
- 新增测试覆盖以上 3 个场景。

**涉及文件**：`src/ui/app.mjs`、`src/core/settings.mjs`、`src/printing/settings-store.mjs`（如需要）、`tests/settings-store.test.mjs`、`tests/compliance-label-dom.test.mjs`。

**实现备注**

- 逐项校验放在 app 层还是 settings client 层均可，但必须保证 UI 能拿到「跳过列表」。
- 若选择「加载不完整时完全禁止保存」，也满足数据安全要求，但 UX 较差；推荐逐项容错。
- 不要把 `defaultTemplates()` 作为任何保存操作的起点。

### 3.2 REQ-ERR-01（P1）错误归一化与 CODE128 内容校验

**问题**

`src/printing/design-svg.mjs:29` 与非设计模板的 `barcodeSvg()` 直接调用 JsBarcode。仓库自带版本在非法输入时抛出**字符串**（实测：`typeof === 'string'`，`message === undefined`，内容形如 `"黑色" is not a valid input for e`）。`app.mjs`、`template-designer.mjs` 的所有 catch 都读取 `error.message`，于是显示「保存失败：undefined」「预览失败：undefined」「生成或打开预览失败：undefined」。

**需求**

1. 所有 JsBarcode 调用统一经过一个包装函数：
   - 捕获任意类型（字符串、对象、Error）；
   - 抛出 `new Error('CODE128 只能编码英文字母、数字和常见符号，请修改内容：' + 可读原因)`；
   - 不吞掉 `AbortError`。
2. 新增统一的错误消息提取：`messageOf(error) => error?.message || String(error || '未知错误')`，替换 UI 中直接读取 `error.message` 的位置。
3. 设计器保存时对 `code` 元素做一次真实编码校验（已有 `designSvg(template, sample, barcodeSvg)` 调用，可复用）；错误定位到具体元素名称或 id。
4. CODE128 元素绑定到中文规格（如 `{{skuSpec}}`）时，预览/生成也应给出同一中文提示，而不是崩溃。
5. 空文本的 CODE128 元素：保存时提示「CODE128 内容不能为空」，不允许保存。

**验收标准**

- 设计器中新建 CODE128 元素，输入中文或清空后保存：显示明确中文提示，包含「CODE128」，不出现 `undefined`。
- 同一模板的预览、生成 PDF 两条路径均不出现 `undefined`。
- 正常数字/字母条码输出与 v1.4.8 一致。
- 新增测试：分别用中文、空字符串、合法数字调用渲染，断言错误类型为 `Error` 且消息可读；合法输入输出不变。

**涉及文件**：`src/printing/design-svg.mjs`、`src/printing/render.mjs`、`src/ui/app.mjs`、`src/ui/template-designer.mjs`、`tests/render-design-sample.mjs` 或新增测试文件。

### 3.3 REQ-RENDER-01（P1）内容缩放参与换行与高度适配

**问题**

`src/printing/render.mjs` 的 `renderSimple()` 先用未缩放的 `usableWidth` 和 `textHeight` 决定换行与字号，随后才 `context.translate(...); context.scale(content.scale / 100, ...)` 绘制。内容缩放 > 100% 时文字会超出右边界并被画布裁切，纵向也会进入条码区。

**实测**：60 × 40 mm 模板、150% 内容缩放、150 DPI，画布宽 354 px，最后一列（x=353）存在暗像素；文字暗像素延伸到 y=136，超过上半区 48% 的高度。

**需求**

1. 换行宽度按 `contentScale` 修正：`usableWidth = (canvas.width - margin * 2) / contentScale`。
2. 高度判断按 `contentScale` 修正：`lines.length * size * 1.35 * contentScale <= textHeight`。
3. 缩放范围仍为 50–150%；100% 时输出必须与当前版本逐像素一致（回归基线）。
4. 若产品决定保留「放大即裁切」的语义，则必须在界面明确提示，并关闭自动缩小字号的误导；默认按本需求实现适配。

**验收标准**

- 150% 缩放渲染后：最后 1 像素列无暗像素；文字不进入下方 52% 区域（以测试钩子记录 `fillText` 的绘制范围，或检查像素）。
- 50%、100%、150% 三档均不抛错，文字行数符合预期。
- 100% 输出与 v1.4.8 的测试基线一致。
- 新增测试覆盖 150% 场景。

**涉及文件**：`src/printing/render.mjs`、`tests/compliance-label.test.mjs` / `tests/compliance-label-dom.test.mjs`。

### 3.4 REQ-PERF-01（P1）保存路径引用短路真正生效

**问题**

`src/core/settings.mjs` 中 `saveSettings()` 在比较前执行 `structuredClone(settings)`，而 `baseline` 也是上一次保存的克隆。`settingsPatch()` 的 `unchanged(left, right)` 永远走不到 `left === right`，仍会对每个模板（含 2.8 MB base64 图片）做两次 `JSON.stringify`，整库深拷贝也照常发生。

**实测**：4 个各含 2 MB 字符串的模板，首次保存 24 ms，内容完全不变的第二次保存 43 ms；`JSON.stringify` 仍被调用。

**需求**

1. 在深拷贝之前，用调用方传入的对象同步计算 patch（或在 `commit` 层生成显式 patch），保证未改动模板保持引用相等。
2. `baseline` 保存的是与页面状态共享引用的对象，而不是立即克隆；如保留克隆，必须保证比较发生在克隆之前。
3. 明确「页面内模板对象不可变」的约束并写入注释；所有写路径（设计器、导入、合并）必须继续创建新对象，不得原地修改。
4. 只克隆真正需要异步传输的 patch 内容。

**验收标准**

- 新增测试：对未改动模板的保存，`JSON.stringify` 不接收该模板对象（可通过 spy/包装全局函数断言）。
- 8 MB 库、内容未变的保存，实测 ≤ 20 ms（同一台开发机）。
- 保存内容、冲突合并、删除语义与 v1.4.8 一致；现有 settings 测试全绿。

**涉及文件**：`src/core/settings.mjs`、`src/ui/app.mjs`、`tests/settings-store.test.mjs`。

**备注**：上一版审查文档中的 PERF-1 标记为已实现，但引用短路未在真实保存路径生效；完成本需求后同步修正文档状态。

### 3.5 REQ-PDF-01（P1）PDF 体积预检与生成中止

**问题**

`MAX_PAGES = 10000` 只限制页数，12 MB 体积上限在 `services.openPdf()`（`src/integration/bridge.mjs`）中、即 `generatePdf()` 完成之后才检查。用户可能等待数分钟后才收到「PDF 超过 12 MB」。

**实测**（70 × 40 mm 简单模板）：300 DPI 单标签压缩后约 2.7 KB，600 DPI 约 5.8 KB，PDF 每页额外约 0.18 KB。因此 300 DPI 约 4 000 个不同标签、600 DPI 约 2 000 个就会触及 12 MB；含照片的设计模板每标签可能几十到上百 KB。

**需求**

1. **生成前粗估**：根据「唯一标签数 × 每 DPI 估算字节 + 页数 × 0.2 KB × 安全系数 1.3」估算；超过 10 MB 时提示用户，并给出「减少唯一 SKU 数 / 改用 300 DPI / 分批打印」的建议。
2. **生成中硬中止**：在 `embedMonochrome()` 累计压缩字节（或 `pdf.save()` 前的等价指标）超过 11.5 MB 时抛错并中止，返回中文提示；已生成的部分不写入 IndexedDB。
3. **上限一致性**：`MAX_PAGES` 可根据 DPI 或唯一标签数进一步收紧；不得出现「页数合法但体积必然超限」的组合。
4. 提示文案区分「页数超限」「体积超限」「数量过多建议分批」三类。
5. 正常规模（例如 100–500 张）不得因估算偏保守被误拒。

**验收标准**

- 构造 5 000 个唯一 SKU、300 DPI 的简单模板任务：在开始渲染前或渲染早期被拒绝，消息包含「分批」或「12 MB」，且不产生 PDF 标签页。
- 构造 2 000 个唯一 SKU、600 DPI：同样提前拒绝。
- 100 个唯一 SKU、300 DPI：正常生成，页数与输出不变。
- 新增测试：用桩替换渲染器，验证预算计算与中止路径。

**涉及文件**：`src/core/core.mjs`、`src/printing/render.mjs`、`src/ui/app.mjs`、`src/integration/bridge.mjs`（保留最终兜底）、`tests/compliance-label.test.mjs`。

### 3.6 REQ-BACKUP-01（P2）备份数量上限与可创建规模对齐

**问题**：`src/core/template-backup.mjs` 限制 1–500 个模板，但 UI 和存储允许创建超过 500 个小模板；达到 501 个后「备份全部模板」直接失败。

**需求**：二选一并在文档中说明：

- 方案 A（推荐）：提高/移除备份数量上限，仅保留字节上限（16 MB 文件与 10 MB 存储）。
- 方案 B：在创建/导入时限制模板总数 ≤ 500，并给出明确提示。

**验收标准**：501 个各约 1 KB 的模板可以完整导出并重新导入（方案 A）；或第 501 个模板在创建时被明确拒绝（方案 B）。新增对应测试。

### 3.7 REQ-IMG-01（P2）图片保留原格式并按需降采样

**问题**：`src/ui/template-designer.mjs` 的图片导入一律 `canvas.toDataURL('image/png')`，JPEG 照片转 PNG 后体积显著增大，常超过 2.8 MB 被拒绝，或挤占存储配额。

**需求**

1. PNG/WebP 保留原 data URL（WebP 是否保留按 Chrome 解码兼容性确认）；JPEG 保留 `image/jpeg`，不强制转 PNG。
2. 超过 4096 px 的图片按最长边降采样到 4096 以内，再编码。
3. 单图 data URL 仍 ≤ 2.8 MB；超过时优先降低质量/尺寸，而不是直接失败（若无法降到达标再提示）。
4. 备份/导出/导入保持同一 data URL 字符串，不改变既有模板。

**验收标准**：导入 2 MB JPEG 后模板中 `src` 以 `data:image/jpeg` 开头，长度不超过源文件 base64 太多；导入 8000 px 图片被降采样且打印正常；现有图片模板逐像素输出不变。

**涉及文件**：`src/ui/template-designer.mjs`、`src/core/design.mjs`（如需要放宽/校验格式）。

### 3.8 REQ-ORIGIN-01（P2）面板产地输入持久化

**问题**：面板中的「条码区域产地」只在当前输入框生效，切换模板或刷新页面即恢复模板原值。

**需求**：输入防抖 300–500 ms 后写回当前模板的 `origin` 并保存（走现有 `commit()`），或作为独立设置持久化；切换模板时显示对应模板的值。保存失败时保留输入并提示，不阻塞打印。

**验收标准**：修改产地 → 等待防抖 → 刷新页面/切换模板再切回，值仍在；`settingsPatch` 只提交该模板；输入过程中的失败有可读提示。

**涉及文件**：`src/ui/app.mjs`、`src/core/settings.mjs`（如需新字段）、`tests/compliance-label-dom.test.mjs`。

### 3.9 REQ-FETCH-01（P2）翻译接口失败可降级

**问题**：`fetchLabels()` 中翻译请求失败会使整次读取失败。已有「未返回翻译时保留原文并提示」的分支，可复用。

**需求**：捕获 `batchQuery` 的请求错误，保留中文规格，追加 warning（如「英文规格翻译失败，已保留原文，请核对」），继续返回其余数据；非翻译请求（商品/数量）失败仍按现有策略整体失败。

**验收标准**：桩使翻译请求抛错，仍返回记录与中文规格，warning 含「翻译失败」；正常路径输出不变。

**涉及文件**：`src/core/core.mjs`、`tests/compliance-label.test.mjs`。

### 3.10 REQ-LOAD-01（P2）面板延迟加载

**问题**：`src/integration/loader.js` 在每个支持的商家页 `document_idle` 立即导入整个 app、挂载 Shadow DOM 并读取模板存储。

**需求**

1. 页面加载时仅注入轻量入口（launcher 与消息监听），首次点击 launcher 或收到 `OPEN_PANEL` 时再动态导入 app 并挂载。
2. 保持 `pageType()` 对 launcher 显隐的判断；不支持的页面不加载 app。
3. 防止并发重复挂载；导入失败时保持可重试。
4. 不改变现有消息协议与 shadow DOM 结构。

**验收标准**：普通商家页面加载后，在未点击/未收到 popup 消息前，后台不收到 `SETTINGS_REQUEST`；点击 launcher 后功能与 v1.4.8 一致；popup 打开面板仍可用；重复点击不产生第二份 UI。

**涉及文件**：`src/integration/loader.js`、`src/ui/app.mjs`（如需拆分 mount 与样式加载）。

### 3.11 REQ-PROGRESS-01（P2）PDF 进度更新节流

**问题**：`generatePdf()` 每个 job 调用一次 `onProgress`，最多 10 000 次 DOM 更新。

**需求**：仅在百分比变化或距上次更新 ≥ 100 ms 时通知；结束与取消仍保证最终状态一致。

**验收标准**：1 000 页任务中 `onProgress` 调用次数显著下降（例如 ≤ 100）；进度最终到 100%；取消路径不变。

**涉及文件**：`src/printing/render.mjs`、`tests/compliance-label.test.mjs`。

---

### 3.12 REQ-FOOTPRINT-01（P2）存储占用按字节估算

**问题**：`src/core/footprint.mjs` 用 `string.length` 估算，中文文本在 UTF-8 下可能占 2–3 倍，存在「预检通过、浏览器配额拒绝」的边角情况。

**需求**：文本字段按 UTF-8 字节估算（`TextEncoder` 或等价），图片 base64 按 ASCII 长度；预算仍保留余量；错误提示中的占用数字与估算口径一致。

**验收标准**：构造大量中文文本元素，估算值与 `new TextEncoder().encode(JSON.stringify(settings)).length` 的偏差 ≤ 5%（或估算值不小于实际）；现有配额测试仍按预期拒绝。

**涉及文件**：`src/core/footprint.mjs`、`src/printing/settings-store.mjs`、`tests/settings-store.test.mjs`。

---

### 3.13 REQ-PRINT-01（P3）打印页加载失败反馈

**问题**：`src/printing/print.mjs` 只监听 iframe `load`；PDF 损坏或加载失败时状态永久停留在「正在加载 PDF…」。

**需求**：增加 `error` 监听与超时（如 10 s）；失败时提示重新生成或使用下载链接；成功路径不变。

**验收标准**：桩造 iframe 错误，页面显示可读中文提示；正常 PDF 仍可打印/下载。

**涉及文件**：`src/printing/print.mjs`、`src/printing/print.html`（如需要）。

### 3.14 REQ-BUILD-01（P2）行尾规范与可重复构建

**问题**：仓库缺少 `.gitattributes`，本机 `core.autocrlf=true`，工作区存在 LF/CRLF 混合（如 README 为 CRLF、部分源码为 LF）。在不同机器/重新 checkout 后，ZIP 字节可能不同，与「产物可重复」的说明不一致。

**需求**

1. 新增 `.gitattributes`：至少对 `*.mjs`、`*.js`、`*.css`、`*.html`、`*.json`、`*.md` 统一 `eol=lf`；必要时 `* text=auto`。
2. 规范化后重新生成 `dist/`，确认 `npm run check` 与现有 vendor 校验通过。
3. 文档说明：同一次 checkout、同一 Node/zlib 版本下产物可重复；跨平台依赖统一行尾。
4. CI 增加一次「构建两次并比较 sha256」的步骤（同机器），防止非确定性回归。

**验收标准**：新建 `.gitattributes` 后 `git status` 干净；`npm run build` 连续两次 sha256 相同；CI 通过；README 的说明与实际一致。

**涉及文件**：`.gitattributes`、`README.md`、`.github/workflows/ci.yml`、`scripts/build.mjs`（如需要）。
