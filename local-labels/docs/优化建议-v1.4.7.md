## 2. 性能热点

### PERF-1 保存路径的深比较与深拷贝（P0）

**位置**：`src/core/settings.mjs:4`、`:13`、`:16`；`src/ui/app.mjs:72`

**现象**：`settingsPatch()` 用 `JSON.stringify` 做深比较；`saveSettings()` 在比较之前先 `structuredClone(settings)`。模板可能内嵌最大 2.8 MB 的 base64 图片，因此每一次"切换模板""保存位置""保存模板"都会：

1. `structuredClone(settings)` —— 深拷贝整库（`settings.mjs:13`）
2. 对每个模板各 stringify 两次 —— 生成后又立刻丢弃（`settings.mjs:4`、`:30`）
3. 后台 `applySettingsPatch()` 再对每个模板跑一遍 `localTemplate()` 全量校验，其中包含对整段 base64 的正则匹配（`settings.mjs:46`）

**为什么可以省**：`state.local` 里的模板对象在保存时绝大多数保持引用不变——`filter`、`push`、`{ ...template, layout }` 都只影响被改动的那个元素。加一层引用短路即可吃掉绝大部分开销。

**建议改法**：

```js
// src/core/settings.mjs
const unchanged = (left, right) => left === right || same(left, right);

export function settingsPatch(previous = {}, next = {}) {
  const patch = {};
  if (Array.isArray(next.templates)) {
    const before = keyed(previous.templates), after = keyed(next.templates);
    patch.templates = [...after.values()].filter(template => !unchanged(before.get(template.id), template));
    patch.deletedTemplates = [...before.keys()].filter(id => !after.has(id));
  }
  // ...
}
```

`unchanged(undefined, template)` 在新增模板时仍为 `false`，语义不变。

**关于 `structuredClone`**：本次通读了所有写路径——设计器编辑的是 `draft` 克隆，`layoutEditor.apply()` 返回新对象，`mergeTemplateBackup()` 构造新数组，没有任何一处原地修改模板。因此 `settings.mjs:13` 的克隆并非必需。但它目前是"基线不被意外改写"的唯一保险，建议**先只做引用短路、实测收益，再决定是否移除克隆**；若移除，请补一条注释说明"页面内模板对象视为不可变"，并在 `settings-store.test.mjs` 里加一条断言防回归。

**验收**：构造 5 个各含 1 MB 图片的模板，在 DevTools Performance 面板对比"切换模板"的耗时；`settings-store.test.mjs`、`template-backup.test.mjs` 全绿。

### PERF-2 设计器的全量校验（P0）

**位置**：`src/ui/template-designer.mjs:49`；`src/core/design.mjs:17-48`

**现象**：

```js
function mutate(action) {
  if (saving) return false; finishGesture(); const before = snapshot();
  try { action(); localTemplate(draft); commit(before); paintAll(); return true; }
  // ...
}
```

每一次对齐、方向键微调、图层上下移、复制、删除、隐藏/锁定，都会把**全部最多 120 个元素**重新校验一遍；只要模板里有图片，`design.mjs:42` 的 `/^data:image\/(png|jpeg|webp);base64,[a-z0-9+/]+={0,2}$/i` 就要对 2.8 MB 字符串整体匹配一次。拖动手势走的是 `schedulePatch()` 不受影响，但键盘微调和属性面板操作会连续触发。

**为什么可以省**：编辑期间图片 payload 从未改变——它是用户在文件选择器里导入、经 canvas 重新编码后写入的，长度和字符集在上传那一刻就已确定。反复校验没有安全收益。

**建议改法**：把校验拆成两级，编辑期用廉价结构校验，真正落盘/导入时再跑完整正则。

```js
// src/core/design.mjs
const IMAGE_SRC = /^data:image\/(png|jpeg|webp);base64,[a-z0-9+/]+={0,2}$/i;
const IMAGE_PREFIX = /^data:image\/(png|jpeg|webp);base64,/i;

export function validateDesign(template, width = Number(template.width), height = Number(template.height), { trustImages = false } = {}) {
  // ...
  if (value.type === 'image') {
    if (typeof value.src !== 'string' || value.src.length > 2800000) throw new Error('图片必须是本机导入的 PNG/JPEG/WebP，每张不超过 2 MB。');
    if (!(trustImages ? IMAGE_PREFIX : IMAGE_SRC).test(value.src)) throw new Error('图片必须是本机导入的 PNG/JPEG/WebP，每张不超过 2 MB。');
    // ...
  }
}
```

再把 `options` 沿调用链透传：`localTemplate(value, options)` → `validateTemplate(value, options)` → `validateDesign(template, width, height, options)`。设计器里改为：

```js
localTemplate(draft, { trustImages: true });   // template-designer.mjs:49
```

而 `template-designer.mjs:256`（保存提交）保持 `localTemplate(draft)` 的完整校验不变——那是唯一值得付出代价的位置。

**验收**：`template-designer.test.mjs`（含"图片嵌入""无效字段阻止保存"两条）保持全绿；手工验证导入一张 2 MB 图片后拖动/微调不再掉帧。

### PERF-3 简单模板的条码双渲染（P1）

**位置**：`src/printing/render.mjs:145-151`

**现象**：

```js
const initialSvg = barcodeSvg(record, template.origin);              // 完整渲染一遍
const dimensions = new DOMParser().parseFromString(initialSvg, 'image/svg+xml').documentElement;
const naturalWidth = Number(dimensions.getAttribute('width')), naturalHeight = Number(dimensions.getAttribute('height'));
// ...
const svg = barcodeSvg(record, template.origin, globalThis.JsBarcode, { layout, unitMm });  // 再完整渲染一遍
```

第一次渲染的产物只用来读两个数字。而 `barcodeSvg()` 内部包含 `JsBarcode` 编码、`XMLSerializer` 序列化、以及 5 段文字的 `measureText` 自适应字号。

**建议改法**：把 JsBarcode 的产物按 `labelCode` 缓存起来，并暴露一个只读度量的入口。

```js
// src/printing/render.mjs
const barcodeCache = new Map();   // `${barsHeight}:${labelCode}` -> { bars, barsWidth }

function encodeBars(labelCode, JsBarcode, barsHeight = 106) {
  const key = `${barsHeight}:${labelCode}`;
  const hit = barcodeCache.get(key);
  if (hit) return hit;
  const svg = document.createElementNS('http://www.w3.org/2000/svg', 'svg');
  JsBarcode(svg, String(labelCode), { format: 'CODE128', width: 1, height: barsHeight, margin: 0, displayValue: false });
  const group = svg.querySelector('g'), barsWidth = parseFloat(svg.getAttribute('width'));
  if (!group || !Number.isFinite(barsWidth) || barsWidth < 1 || barsWidth > 2000) throw new Error('条码尺寸无效或内容过长。');
  const entry = { bars: group, barsWidth };
  if (barcodeCache.size >= 256) barcodeCache.delete(barcodeCache.keys().next().value);
  barcodeCache.set(key, entry);
  return entry;
}

export const barcodeMetrics = (record, JsBarcode = globalThis.JsBarcode) => encodeBars(record.labelCode, JsBarcode);
```

`barcodeSvg()` 改为复用 `encodeBars()` 的结果；`renderSimple()` 先取 `barcodeMetrics()` 算 `unitMm`，然后只调用一次 `barcodeSvg()`。净效果：每条标签一次 JsBarcode、一次完整 SVG 构建。

**风险**：缓存的是 DOM 节点，`serializeToString` 每次仍会重新序列化（必须如此，因为要拼进不同的 viewBox）；但 `bars` 节点在多次序列化之间只读，安全。注意 `barsHeight` 已进入 key，避免未来改动高度时串味。

### PERF-4 `yieldFrame` 的定时器钳制（P1）

**位置**：`src/printing/render.mjs:8`、`:287`

```js
const yieldFrame = () => new Promise(resolve => setTimeout(resolve, 0));
// ...
for (const job of jobs) { /* ... */ await yieldFrame(); }
```

Chrome 对嵌套的 `setTimeout` 有 4 ms 最小间隔（第 5 层嵌套之后生效）。异步函数在定时器回调里继续 await，会把嵌套层级一路累加，于是这个循环里每个 job 至少付出约 4 ms 的纯调度开销。1 000 个唯一标签就是约 4 秒。命中缓存时（同一标签只 append 页面）这部分开销占比更高。

**建议改法**：用 `MessageChannel`（0 ms，不触发钳制）或在支持的浏览器上用 `scheduler.postTask`：

```js
const channel = new MessageChannel();
const yieldFrame = () => new Promise(resolve => {
  channel.port1.onmessage = () => resolve();
  channel.port2.postMessage(0);
});
```

`MessageChannel` 版本要求同一时刻只有一个未完成的 await（当前循环满足该条件）。

### MAINT-1 卖家域名判定抄了两份（P1）

**位置**：`src/printing/background.mjs:9` 与 `:16` —— 两行**完全相同**的正则：

/^https:\/\/(seller\.kuajingmaihuo\.com|agentseller(?:-us|-eu)?\.temu\.com|seller\.temu\.com)\//

### MAINT-2 两套字符级换行（P1）

**位置**：`src/printing/render.mjs:79` `wrapText()` 与 `src/printing/design-svg.mjs:6` `textLines()`

两者是同一套"逐字符累加 + `measureText` 超宽则换行"逻辑的两个副本，只差字体设置和宽度来源（像素 vs 毫米 ×10）。

**建议改法**：抽 `src/printing/text-fit.mjs`：

```js
export function fitLines(context, text, maxWidth) {
  const lines = [];
  for (const paragraph of String(text).split('\n')) {
    let line = '';
    for (const char of paragraph) {
      if (line && context.measureText(line + char).width > maxWidth) { lines.push(line); line = ''; }
      line += char;
    }
    lines.push(line);
  }
  return lines;
}
```

两边各自只保留"设置字体、算最大宽度"的差异部分。

**顺带（低优先级）**：这个算法的 `measureText` 次数约为字符数的两倍，在 1 500 字的 `warning` 字段上仍可接受；`renderSimple` 的字号搜索循环（`render.mjs:133-138`，300 DPI 下约 5 轮）会把它乘以 5。如果后续实测偏慢，可改为"先用整段宽度估算行数，再对候选字号二分"，但**在没有实测数据前不建议动**——当前实现正确性优先，且已被测试覆盖。

### MAINT-3 两套变量替换，且与文档不一致（P1，含行为缺陷）

**位置**：`src/printing/render.mjs:35` 与 `src/core/design.mjs:93`

| 实现 | 支持变量 |
| --- | --- |
| `render.mjs` 的 `variables()` | `sku`、`skc`、`skuSpec`、`skcSpec`、`sourceId` |
| `design.mjs` 的 `designVariables()` | 上述 5 个 + `labelCode`、`origin` |

而 `docs/usage.md:46` 明确承诺支持全部 7 个。结果是：**可视化模板（`qingyin-design/v1`）能用 `{{labelCode}}` 和 `{{origin}}`，老的 `qingyin-template/v1` 文字模板里写了会被静默替换成空字符串**——用户不会收到任何提示。

**建议改法**：删除 `render.mjs` 的 `variables()`，统一用 `designVariables()`：

// src/printing/render.mjs
import { designVariables } from '../core/design.mjs';
// renderSimple 内：
.map(text => designVariables(text, record, template.origin))

**注意这是行为变更**：老模板里写了 `{{labelCode}}` 的，以前输出空字符串，之后会输出真实条码值。这属于修复文档已承诺的能力，但应在 `CHANGELOG.md` 里单独列一条，避免用户以为标签内容"突然变了"。

**验收**：`compliance-label.test.mjs`（模板格式与变量相关用例）与 `template-designer.test.mjs`（变量替换）保持全绿，另补一条针对 `{{origin}}` 的用例。

### MAINT-4 `app.mjs` 的手工状态同步（P2）

**位置**：`src/ui/app.mjs:101-108`、`:269-275`、`:283-292`、`:293-303`

同样的五件套被手写了四遍：

```js
state.local = next; state.selected = data.id; state.layouts = layouts;
layoutEditor.forget(data.id); previewRendererCache = undefined;
$('#origin').value = data.origin; renderTemplates(); await refreshPreview();
```

漏掉其中任意一句，就会出现"模板已切换但预览还是旧的"这类很难复现的问题。建议收口成：

```js
async function commit({ local = state.local, selected = state.selected, layouts = state.layouts }, message) {
  await save({ templates: local, selected, layouts });
  Object.assign(state, { local, selected, layouts });
  layoutEditor.forget(selected); previewRendererCache = undefined;
  $('#origin').value = chosen()?.origin ?? 'China';
  renderTemplates(); await refreshPreview();
  if (message) notice(message);
}
```

`app.mjs` 是最大的单文件（376 行、单函数 `mountLabelApp`），但**不建议拆分**——它整块就是这一个面板的生命周期，拆开反而要多传一层状态。只做这一处收口即可。

## 4. 工程化缺口

### TOOL-1 缺少项目骨架与 CI（P2）

现状：没有根 `package.json`、没有 `.editorconfig`、没有 ESLint / Prettier、没有 CI。所有命令都要手敲，且 `scripts/check.mjs` 只在构建里被间接调用。

建议在 `local-labels/` 下新增：

```json
{
  "name": "qingyin-label-helper",
  "private": true,
  "type": "module",
  "scripts": {
    "check": "node scripts/check.mjs",
    "test": "npm --prefix tests test",
    "build": "node scripts/build.mjs",
    "format": "prettier --write \"src/**/*.{mjs,css,html}\" \"scripts/**/*.mjs\" \"tests/**/*.mjs\""
  },
  "devDependencies": {
    "prettier": "^3.3.3"
  }
}
```

配 `.github/workflows/ci.yml`：

```yaml
name: ci
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm, cache-dependency-path: tests/package-lock.json }
      - run: npm --prefix tests ci

      - run: npm run build
```

已经有 56 个测试，CI 的边际成本很低、拦截回归的价值很高。

**注意**：引入 Prettier 会重排现有代码，尤其 `src/ui/style.css` —— 它现在是 8 行、单行最长 5 795 字符，几乎无法 diff 和 review。建议**把格式化单独作为一个提交**，并且不要放在功能改动里，否则 review 会被淹没。构建阶段并不压缩 CSS，所以现在的压行没有任何收益，只是牺牲可读性。

### TOOL-2 构建依赖外部 `python`（P2）

**位置**：`scripts/build.mjs:52`

```js
const result = spawnSync('python', ['-c', python, moduleRoot, archive, list], { encoding: 'utf8', windowsHide: true });
```

这是一个纯 Node 项目里唯一的非 Node 依赖。在 Windows 上，`python` 经常被 Microsoft Store 的别名劫持，退出码 9009 且报错极难懂；在 CI 或没装 Python 的机器上直接构建失败。

`build.mjs` 里那些 `assert`（清单资源齐全、不含 `tests/`、`dist/`、`subplugin-ide/`、不含 `declarative_net_request`、解包后逐个核对）是整个构建里最有价值的部分，值得保留，但不该跑在 Python 字符串里。

**建议改法**：用 `node:zlib` 写一个约 40 行的 zip writer，把断言改回 JS（顺便能给出更友好的错误信息）。

```js
import { deflateRawSync } from 'node:zlib';

const CRC = (() => {
  const table = new Int32Array(256);
  for (let n = 0; n < 256; n++) { let c = n; for (let k = 0; k < 8; k++) c = c & 1 ? 0xedb88320 ^ (c >>> 1) : c >>> 1; table[n] = c; }
  return table;
})();
const crc32 = buffer => { let c = -1; for (const byte of buffer) c = CRC[(c ^ byte) & 0xff] ^ (c >>> 8); return (c ^ -1) >>> 0; };

// entries: [{ name, data: Buffer }] -> Buffer
function zip(entries) {
  const parts = [], central = [];
  let offset = 0;
  for (const { name, data } of entries) {
    const body = deflateRawSync(data, { level: 6 }), nameBytes = Buffer.from(name, 'utf8'), crc = crc32(data);
    const local = Buffer.alloc(30);
    local.writeUInt32LE(0x04034b50, 0); local.writeUInt16LE(20, 4); local.writeUInt16LE(0x0800, 6);
    local.writeUInt16LE(8, 8); local.writeUInt16LE(0, 10); local.writeUInt16LE(0x21, 12);
    local.writeUInt32LE(crc, 14); local.writeUInt32LE(body.length, 18); local.writeUInt32LE(data.length, 22);
    local.writeUInt16LE(nameBytes.length, 26); local.writeUInt16LE(0, 28);
    parts.push(local, nameBytes, body);

    const entry = Buffer.alloc(46);
    entry.writeUInt32LE(0x02014b50, 0); entry.writeUInt16LE(20, 4); entry.writeUInt16LE(20, 6);
    entry.writeUInt16LE(0x0800, 8); entry.writeUInt16LE(8, 10); entry.writeUInt16LE(0, 12); entry.writeUInt16LE(0x21, 14);
    entry.writeUInt32LE(crc, 16); entry.writeUInt32LE(body.length, 20); entry.writeUInt32LE(data.length, 24);
    entry.writeUInt16LE(nameBytes.length, 28); entry.writeUInt32LE(offset, 42);
    central.push(entry, nameBytes);
    offset += local.length + nameBytes.length + body.length;
  }
  const directory = Buffer.concat(central), end = Buffer.alloc(22);
  end.writeUInt32LE(0x06054b50, 0); end.writeUInt16LE(entries.length, 8); end.writeUInt16LE(entries.length, 10);
  end.writeUInt32LE(directory.length, 12); end.writeUInt32LE(offset, 16);
  return Buffer.concat([...parts, directory, end]);
}
```

**验收**：`standalone.test.mjs` 原本就会"复制到无父项目的临时目录后重新构建并解包"，改完跑一遍即可；另外用系统解压工具打开一次 `dist/qingyin-label-helper.zip`，确认中文文件名与目录结构正常（UTF-8 标志位 `0x0800` 已设置）。

**保底方案**：若暂时不想重写，至少在 `spawnSync` 失败时区分"找不到 Python"与"断言失败"，给出可操作的提示。

### TOOL-3 缺 `minimum_chrome_version`（P2）

`manifest.json` 使用了 `"world": "MAIN"`（Chrome **111+** 才支持）以及 `structuredClone`（98+）、`Object.hasOwn`（93+）、`crypto.randomUUID`（92+）。低版本 Chrome 上 MAIN world 注入会**静默失败**，用户只会看到"点了没反应"，而这恰恰是最难远程诊断的故障类型。

```json
"minimum_chrome_version": "111",
```

放在 `manifest_version` 之后即可。成本一行，收益是把一类"玄学故障"变成扩展管理页上的明确提示。

## 5. 两个需要决策的风险项

### RISK-1 存储配额与允许规模冲突

**事实链**：

- `manifest.json` 只申请了 `storage`，且 `scripts/check.mjs:28` 把权限白名单**硬编码**为 `['storage', 'activeTab']`
- 因此 `chrome.storage.local` 的上限是默认的 10 MB（10 485 760 字节），没有 `unlimitedStorage`
- 而所有模板存在**同一个 key** `qingyinLabelSettings` 里（`settings-store.mjs:8`）
- 单模板图片上限约 5 MB（`design.mjs:48` 的 `6500000` 字符）
- 备份允许最多 500 个模板（`template-backup.mjs:7`）

也就是说，**两个带大图的模板就可能撑爆配额**。当前体验是保存时才抛错（`settings-store.mjs:22` 的文案写得不错，但属于事后诸葛）——用户可能已经编辑了二十分钟，才在点保存时被拒。

**方向一（保守，推荐）**：在导入/新建时就做总字节预算校验。例如在 `design.mjs` 增加：

```js
export const STORAGE_BUDGET_BYTES = 8 * 1024 * 1024;   // 留 20% 余量给 schema 与当前位置

export function settingsFootprint(settings) {
  return new TextEncoder().encode(JSON.stringify(settings)).length;
}
```

超过预算时提示"当前模板占 8.4 MB，超出浏览器为本扩展保留的空间；请先删除不用的模板或缩小图片"，并给出可删除的候选（按图片字节降序）。

**方向二（激进）**：申请 `unlimitedStorage`。代价是要改 `check.mjs:28` 的白名单，并且削弱"最小权限"这一卖点，商店审核也更可能追问用途。

**建议**：先做方向一。它不改变权限面，且把"事后失败"变成"事前可理解"。

---

### RISK-2 24 MB PDF 的 base64 往返

**位置**：`src/integration/bridge.mjs:20-22`、`src/printing/background.mjs:22-24`

页面侧先拼一个 24 MB 的 latin1 字符串再 `btoa`（字符串约 24 MB，base64 约 32 MB），后台再 `atob` 加 `Uint8Array.from` 还原。峰值内存大约 100 MB，而且这个大字符串要经过一次 `chrome.runtime` IPC 序列化。

**方向一（推荐）**：页面侧直接写 IndexedDB，只把 id 发给后台。后台本来也只是把 blob 存进 IndexedDB 再开一个 tab（`background.mjs:27-31`），这条 base64 通道完全是多余的搬运。副作用是 `pdf-store.mjs` 需要在 content script 世界里可用——它只依赖 `indexedDB` 全局对象，可以直接复用。

**方向二（最小改动）**：把上限从 24 MB 降到 12 MB，并把文案中的"减少商品数量或打印分辨率"改为更具体的引导。

**建议**：若近期没有大单量需求，方向二的投入产出比更高；若已有用户反馈"生成失败"，则做方向一。

## 8. 明确不建议做的事

写下来是为了避免后续过度工程。以下几项在当前规模下收益为负：

- **不要引入框架或打包器**。现在的零构建（源码可直接加载为扩展）是巨大优势：改了代码刷新页面就生效，没有 sourcemap、没有 build 产物与源码不一致的问题。引入 Vue/React + Vite 会把 2 100 行换来一整套构建负担。
- **不要重写成 TypeScript**。项目已有完善的运行时校验（`validateTemplate` / `validateDesign` / `normalizeLayout` 三层），类型带来的收益在这里已被覆盖；若确实需要，加 JSDoc `@typedef` 即可，零成本。
- **不要把 `innerHTML` 大段静态模板外置成文件**。Shadow DOM + 模块内联模板避免了 `fetch` 与 CSP 的复杂度，当前写法没有注入风险（所有用户数据走 `textContent` 或 `xml()` 转义）。
- **不要为了"减少文件数"合并模块**。`core` / `integration` / `printing` / `ui` 的切分与 `scripts/page-resources.mjs` 的依赖图审计是配套的，合并会让"页面能否加载到某个模块"变得难以验证。
